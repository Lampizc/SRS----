## 一、分工原则

1. **按技术模块切，不按申报书章节切**。每人负责一条能从输入跑到输出的代码链路，以及一个可以独立回答的科学问题。这样任何一个人卡住，其他人仍能推进。
2. **先定接口，后写实现**。第 1 个月内必须把数据结构（第四节）定死并冻结，之后只增字段不改字段。
3. **每人一条主线 + 一个交叉复核对象**。复核对象选与自己接口相邻的人，这样 review 是真正看得懂的。
4. **前期用"合成数据"解耦并行**。调度、分组、误差预算这三块在估计器还没做完时，可以先用注入的合成误差/合成角度跑通，不必串联等待。这是 4 人能在 12 个月内做完的关键。

## 三、逐人任务书

### 同学 A（队长）— 地基 + 集成

**为什么是你**：模块 1 是所有人的上游，接口由你定最省事；同时队长必须掌握全局才能做集成和对外汇报，这与你天然重合。

**科学问题**：在 64×64 阵列、只保留 B 个 DFT 波束的有限观测下，用户方向偏离格点、预测有偏差、上下行波长不同，各自会让角度估计产生多大损失？可辨识性对观测窗半宽的要求是什么？

**技术清单**
- 轨道几何：600 km 高度 + 30° 仰角 → 服务区、可见性、过境时长与几何时变
- 二维方向余弦 → 归一化空间频率 (u, v) → DFT 格点索引的坐标转换链
- 阵列流形与 DFT 波束域投影；FDD 下用下行波长重建下行流形（几何角互易、流形不互易）
- SRS 资源配置层：comb、符号数、循环移位、跳频，按 3GPP TS 38.211/38.214 做一层映射，避免仿真与标准脱节
- 三类场景布局（均匀/热点/走廊）+ 三类移动类型（静止/行人/车辆）
- 平台集成：统一 config、日志、指标输出

**额外职责**：进度跟踪、组会组织、与王老师对接、经费与材料、论文与结题报告统筹。

**排期优先级（第 1–2 月）**：坐标转换链与阵列流形/DFT 波束域（`array.py`、`obs.py`——符号约定错误是灾难性的，契约自检守的就是这一层）→ 三类场景布局与轨道几何（`scene.py`）→ SRS 标准映射（可放到第 2 月末）。布局生成可请同学 C 或同学 D 打样：他们最清楚下游要什么，顺便提前建立对模块 1 的理解，正好服务第 6 月的交换讲解。

**第 6–9 月追加**：万级规模下逐次测量都做全阵 64×64 的 FFT 会成为瓶颈，Observer 需要一条"直接在波束域生成观测"的快速路径（对应申报书承诺的"分层实现"）。这条归你，M9 前完成。

**注意**：不要把这部分做成"只有你能跑"的私有代码。模块 1 的每个函数都要有单测和一个 demo 脚本。

### 同学 B — 理论最难的一块

**科学问题**：两用户共用一个 SRS、复增益未知时，角度 CRB 相对独立测量膨胀多少？这个膨胀因子如何随角度间隔、波束窗宽、用户数、SNR、阵列维度变化？能否给出闭式或紧上下界？

**技术清单**
- 单用户 CRB 推导 → 与蒙特卡洛 RMSE 对齐（先确认坐标/归一化/SNR 定义没搞错）
- 两用户 FIM 完整推导：把复增益当 nuisance，做 Schur 补消去，得到角度部分的等效 Fisher 信息
- 复现申报书种子结果：一维全模式、两用户、格点间隔 → 约 2.95 倍
- 推广：多用户（3/4/8）、有限波束（窗半宽 1/2/3）、二维 UPA、离格角度、预测偏差
- 组 CRB 的快速算法：不必每次算完整 FIM，找近似或上下界（这是给同学 C用的）
- 解释"逐对通过、整组失败"的机理，给出可计算判据

**这块是全项目最有论文价值的部分**，也是答辩最容易被追问的地方。建议每推进一步就写一段推导笔记，12 月直接拼成论文的理论章节。

### 同学 C — 算法的"能不能用"

**科学问题**：给定精度要求，哪些用户组合可以共用 SRS？整组 CRB 判据相对"支撑分离"（按波束域能量支撑是否重叠、留保护波束）在精度、资源、计算量三个维度上的差异与适用边界是什么？

**技术清单**
- 候选筛选：基于方向间隔 + 波束域支撑，把 O(K²) 的两两比较压到可接受范围
- 整组精度检查：调用同学 B的 CRB 计算器，检查组内**每个**用户是否满足容限
- 执行前复检：按当前预测方向重算，因为用户移动会改变有效间隔
- 不满足时的处置：拆组 → 扩大观测窗 → 改用独立资源，三级降级
- 支撑分离基线实现（保护间隔要先调优，否则对比不公平）
- 大规模优化：角度聚类、图着色、贪心、增量更新；万级用户不能全量重算
- 与支撑分离的精度/资源/计算量三维对照

**提示**：分组是组合问题，容易陷进去。建议先做贪心拿到可用结果，再考虑有没有结构性质（比如给定间隔阈值时贪心是否近似最优）——那是加分项，不是必需项。

### 同学 D — 调度与全部实验

**科学问题**：三类误差（测量、固定偏差、预测）如何合成一个更新周期？符号数 L 与周期 T 怎么联合选最省？在过境几何变化、热点拥挤、批量进入下，超期率与可持续跟踪规模是多少？

**技术清单**
- 预测器 `predict.py`：上一拍估计 → 按用户类型（静止/行人/车辆）运动模型外推 → 下一拍 `theta_pred` / `cov_pred`。它是 Observer 与 Grouper 的共同输入、跟踪闭环的胶水，契约 v1.0.1 起 `Predictor` Protocol 归你；运动模型本来就是你误差预算（pred_rate）的地基，放这里最顺
- 误差预算：σ_meas + b_fixed + σ_pred ≤ ε，测量限按 99% 覆盖校准
- 固定偏差建模：姿态误差、星历误差（关键：**加长测量消不掉**，要能画出"偏差超过多少方法就失效"的边界）
- 预测误差：终端速度、机动范围、经过时间、处理延迟
- L/T 联合优化：总开销约正比于 L/T，在精度约束下搜最优组合
- EDF 调度器：截止期 = 上次测量时刻 + 最大间隔；复用组共同测量；随卫星运动更新分组
- 异常处理：批量进入错峰、集中到期资源预留、跟踪失效重捕
- 性能统计：方向误差及 99% 分位、测量超限率、最大间隔、超期率、探测资源消耗、估计耗时、可持续规模、波束增益损失、SINR
- 全部绘图脚本 + 5 个随机种子的复现包

**这块代码量最大但理论门槛最低，适合作为并行推进的"稳压器"**。前期用合成误差驱动，不依赖同学 B的估计器。

## 四、接口契约（第 1 个月内必须冻结）

这是 4 人协作最容易被忽略、也最容易翻车的地方。建议直接落成 `types.py`：

```
Scene:    sat_track[T] (pos, vel), users[N] (pos, vel, type, access_time), config
Channel:  theta[N, 2]   # 二维方向余弦
          g[N]          # 复增益（幅度+相位）
          snr_db        # 单符号阵列级 SNR
Obs:      Y[B, L]       # 波束域观测：B 个波束 × L 个符号
          beam_idx[B]   # 保留的 DFT 波束索引
Est:      theta_hat[N, 2], crb[N], cov[N,2,2]?, status   # status: ok / ambiguous / lost
Group:    groups[list[list[int]]], L_of_group[dict], fallback_reason
Sched:    plan[(t_slot, group_id, L)], deadline[N]
Metrics:  rmse, p99, overhead_symbols, overdue_rate, max_gap, trackable_scale
```

**三个必须全队统一的约定**（不统一一定出问题）：

1. **坐标与归一化**：方向余弦 u,v 的定义、正负号、是否含 d/λ 因子、DFT 格点是 1/N 还是 2/N。建议写成 `README_coords.md` 并配一个 3 行可运行的验证脚本。
2. **SNR 定义**：申报书写的是"匹配处理后全模式信号总能量与单模式噪声能量之比"。这个口径必须唯一，否则四个人报的 SNR 互相对不上，性能曲线没法比较。
3. **资源计数口径**：一条正交 SRS 序列 = 1 单位；共用不按用户数重复计；多符号按实际符号数累加；初始获取、重捕、控制开销单独记。

**工程约定**：Git 仓库 + 每人一个模块目录 + `main` 分支只接受复核过的 PR；`config.yaml` 是唯一参数真源；所有随机性走统一 `seed` 管理器。

> **v1.0.1 修订（2026-11-05）**：本节已落成 `srs_track/contract.py`（自检 10 项全 PASS）。此次新增 **`Predictor` Protocol，归同学 D**——此前 `theta_pred`/`cov_pred` 被 Observer 与 Grouper 消费却无人生产，"上一拍估计 → 下一拍预测"这段闭环胶水是接口空洞；同时 `Estimate` 增加可选 `cov` 字段（(K,2,2)），缺省时预测器按 Σ ≈ (crb_radius²/2)·I 各向同性换算。预测器模块文件为 `predict.py`。

## 六、协作机制

- **每周一次组会（60 分钟）**：每人 8 分钟讲"上周做了什么、卡在哪、下周要什么"，剩 20 分钟集体解决阻塞项。卡点必须在会上暴露，不允许私下拖两周。
- **代码 review**：由交叉复核人做，重点看接口是否被偷偷改了、随机种子是否固定、指标口径是否一致。
- **文档**：每个模块一个 `README.md`（怎么跑、输入输出、已知限制）；推导笔记单独放 `docs/`。
- **参数表唯一**：任何人改实验参数都要走 `config.yaml`，禁止硬编码。
- **中期交换讲解（第 6 月）**：每人讲一遍相邻模块的代码，能跑通一次。这是防止"某个人一病全组停摆"的最低成本保险。
